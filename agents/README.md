# Как запускать

## Настройка LLM (локально)

1. Скопируйте шаблон окружения и ограничьте права на файл:
   ```bash
   cp .env.example .env
   chmod 600 .env
   ```
2. Впишите свой `LLM_API_KEY` в `.env`. Ключ SiliconFlow можно получить здесь:
   https://cloud.siliconflow.com/me/account/ak
3. Файл `.env` не коммитится и не попадает в Docker-образ. У каждого
   разработчика свой локальный `.env`.
4. Настройки LLM обязательны: без `LLM_BASE_URL` / `LLM_API_KEY` /
   `LLM_MODEL` агент падает с понятной ошибкой при старте.

Проверить настройки без вывода ключа:
```bash
.venv/bin/python -c "from agents.config import get_settings; s=get_settings(); print('base_url:', s.llm_base_url, 'model:', s.llm_model, 'key_set:', bool(s.llm_api_key))"
```

## Использование

RAG-индекс строится снаружи до запуска агента. Агент получает готовый
`RAG` и обращается только к `rag.search_chunks(query)`.

```python
from agents.bootstrap import build_local_service

# RAG уже построен внешним кодом/сервисом
service = build_local_service(rag)
print(service.answer("Какие налоги платит ИП?"))
```

## Как работает агент

```text
parse_dialog -> understand -> clarify
    -> retrieve -> grade -> clarify
    -> generate -> verify -> finalize
    -> rewrite -> retrieve
    -> refuse
```

- История диалога разбирается из текста вида `Пользователь: ...` /
  `Ассистент: ...`.
- `understand` делает standalone-запрос, проверяет тематику и ложные
  предпосылки, делит сложный вопрос на подзапросы и решает, нужен ли
  уточняющий вопрос до поиска.
- `grade` оценивает покрытие каждого подзапроса и проверяет, не найдено ли
  несколько конкурирующих документов с разными номерами договоров.
- `clarify` возвращает уточняющий вопрос пользователю, если запрос неполный
  или неоднозначный.
- `rewrite` переформулирует только проблемные подзапросы.
- `verify` проверяет заземлённость, ссылки и ответ на вопрос.
- Если подтверждённых сведений нет, агент честно отказывается отвечать.

`AgentResult.status` принимает значения `answered`, `partial`, `refused`,
`clarification`. В случае `clarification` поле `AgentResult.clarification`
содержит вопрос и список недостающих сведений.

Лимиты задаются переменными окружения:

- `MAX_SUBQUERIES` (по умолчанию `4`)
- `MAX_RETRIEVAL_ATTEMPTS` (`5`) — сколько поисков разрешено на подзапрос
- `MAX_ANSWER_ATTEMPTS` (`2`)
- `MAX_TOTAL_LLM_CALLS` (`30`)
- `MAX_REWRITE_SUBQUERIES_PER_ROUND` (`4`) — сколько проблемных
  подзапросов переформулировать за один раунд.
- `MAX_TOTAL_TOKENS_PER_QUESTION` (`40000`) — жёсткий бюджет токенов на
  один вопрос.
- `MAX_TOTAL_TOKENS_SOFT` (`30000`) — после этого порога отключаются
  необязательные циклы `rewrite`.
- `HISTORY_LIMIT` (`8`)

Расход токенов учитывается в `used_tokens`. Если провайдер вернул
`usage_metadata`, используются фактические значения; иначе — консервативная
оценка по длине промпта (~1.7 символа на токен, консервативно). Перед вызовом LLM агент
проверяет, хватит ли жёсткого бюджета, и при нехватке использует безопасный
детерминированный fallback.

## Логи

Локальный запуск через `build_local_service` включает логирование: консоль +
файл `logs/llm_<дата_время запуска>.log` в корне репозитория. Один файл на
запуск: время запуска — в имени файла и в первой строке. В лог попадают
промпты и сырые ответы LLM, поэтому после запуска можно изучить, какие
запросы уходили в модель и что она ответила.

Переменные окружения:

- `LOG_LEVEL` (по умолчанию `INFO`) — порог уровня логов. `WARNING` прячет
  промпты и ответы, `DEBUG` показывает больше деталей.
- `LLM_LOG_FILE` — путь к файлу логов. `LLM_LOG_FILE=off` отключает файл
  (останется только консоль). По умолчанию на каждый запуск создаётся новый
  файл в `logs/`.

Для итогового решения логирование в файл не включается: `setup_logging`
вызывается только внутри `build_local_service`, который backend и скрипты
сабмита не используют. Логи не коммитятся: `*.log` уже в `.gitignore`.
